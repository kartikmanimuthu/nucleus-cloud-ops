# Skills Module — Design Spec

**Date:** 2026-07-01
**Status:** Approved (brainstorming complete, pre-implementation)
**Branch:** `skill-memory`

## Problem

Agent "skills" are currently filesystem-based: each skill is a folder
`apps/web-ui/lib/agent/skills/<id>/SKILL.md` (YAML frontmatter `name`/`description`/`tier`
+ markdown body), discovered at runtime by `skill-loader.ts`. There are 8 today. They are
**global / not tenant-scoped** and can only be changed by editing files and redeploying.

We want a dedicated, DB-backed **Skills module** where:

1. Users manually create skills from the console (`source: "user"`).
2. Auto-generated skills (cron/automation, future) are marked `source: "system"`.
3. Skills auto-populate into **both** the AI Ops chat and Agent Ops modules from the DB.
4. The AI Ops console can **convert a chat into a skill** at the end of a conversation.

## Decisions (locked during brainstorming)

- **DB is the sole source of truth.** The filesystem `skill-loader.ts` and all `SKILL.md`
  files are removed entirely. No migration/seeding — the 8 built-ins will be re-created by
  hand through the console.
- **Two origins:** `user` (authored in console, incl. chat→skill conversions) and `system`
  (auto-generated by future cron/automation). Origin is a **badge/label only** — any user
  with the `Skill` permission can edit/disable/delete either kind.
- **Tenant-scoped, shared org-wide.** Every skill belongs to a tenant and is visible to all
  users in that tenant; selectable in both AI Ops and Agent Ops. RBAC governs who can manage.
- **Chat→skill:** LLM distills the transcript into a draft SKILL.md, which opens pre-filled in
  the create-skill dialog for user review/edit before saving (not saved automatically).
- **RBAC:** new dedicated `Skill` subject with full CRUD actions.
- **Aliases dropped:** the old `SKILL_ALIASES` map is not carried over (no legacy IDs to honor).
- **Nav:** Skills is its own top-level nav item (not nested under Agent Ops).
- **Editor:** Monaco for the markdown content field (already in the stack).

## Data Model

New Prisma model in `libs/prisma/schema.prisma`:

```prisma
model Skill {
  id          String   @id @default(cuid())
  tenantId    String
  slug        String   // stable identifier used as `selectedSkill` everywhere (e.g. "cost-analyser")
  name        String
  description String
  tier        String   // 'read-only' | 'mutation' | 'approval-gated'
  content     String   @db.Text   // the SKILL.md markdown body
  source      String   @default("user")  // 'user' | 'system'
  isEnabled   Boolean  @default(true)
  createdBy   String?  // userId who created it (null for system/auto)
  sourceRunId String?  // optional: chat threadId / run it was distilled from
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@unique([tenantId, slug])
  @@index([tenantId])
}
```

- `slug` preserves the existing contract: `AgentOpsRun.selectedSkill`, `ScheduledTask`, and the
  chat `selectedSkill` param all remain string identifiers — no shape change to those models.
- Migration: `cd apps/web-ui && bun run db:migrate`; regenerate both Prisma clients
  (`db:generate` in web-ui and workers) per the dual-generator setup.

## Service / Repository Layer

Replaces `apps/web-ui/lib/agent/skills/skill-loader.ts`.

- New repository `apps/web-ui/lib/db/repositories/skill/` (`interface.ts` + `postgres.ts`),
  registered in the repository factory, **tenant-scoped via `getTenantClient(tenantId)`**.
- New `apps/web-ui/lib/skill-service.ts` exposing the same function names the agents already
  call, but **async + tenant-aware**:
  - `loadSkills(tenantId)` → enabled skills for the tenant
  - `getSkillContent(tenantId, slug)` → markdown body or null
  - `getSkillById(tenantId, slug)` → metadata
  - `getSkillSummaries(tenantId)` → formatted summary string for the evaluator prompt
- A small **per-request cache** (keyed by tenantId) avoids re-querying the DB on every
  reflector/critique loop within a single agent invocation.
- Delete the `apps/web-ui/lib/agent/skills/` directory and all `SKILL.md` files.

### Call sites to update (sync → async + threaded tenantId)

| File | Current | Change |
| ---- | ------- | ------ |
| `lib/agent/prompt-templates.ts` | `buildEffectiveSkillSection(slug)`, `buildBaseIdentity(slug)` sync read | accept `tenantId`, `await` content lookup |
| `lib/agent/fast-agent.ts` | `getSkillContent(slug)` sync | thread tenantId, await |
| `lib/agent/planning-agent.ts` | `getSkillContent(slug)` sync | thread tenantId, await |
| `lib/agent/deep-agent.ts` | `getSkillContent(slug)` sync | thread tenantId, await |
| `lib/agent-ops/executor-graphs.ts` | `loadSkills()` + content sync | thread tenantId, await |

`tenantId` is already available server-side in both the chat route (`tenantId:userId:...`
threadId) and the agent-ops executor (`AgentOpsRun.tenantId`); thread it into the graph config.

## API Routes

All under `apps/web-ui/app/api/skills/`. Responses `{ success, data }` / `{ success, error }`.
Mutations call `authorize(action, 'Skill')` and `AuditService`.

- `GET /api/skills` — list tenant skills (existing route; switch from filesystem to DB,
  add tenant scope). Consumed by both module dropdowns and the console.
- `POST /api/skills` — create (`create` Skill).
- `GET /api/skills/[id]` — fetch one.
- `PATCH /api/skills/[id]` — edit (`update` Skill).
- `DELETE /api/skills/[id]` — delete (`delete` Skill).
- `POST /api/skills/distill` — body `{ threadId }`; runs an LLM pass over the chat transcript
  and returns a **draft** `{ name, description, tier, content }`. Does **not** persist.

## Skills Console (new UI module)

- Nav entry + route `apps/web-ui/app/app/skills/page.tsx`; components under
  `apps/web-ui/components/skills/`.
- **List view:** table/grid — name, description, tier badge, **source badge (User / System)**,
  enabled toggle, created-by, actions.
- **Create/Edit dialog:** React Hook Form + Zod (Zod v4 — use `.issues`), fields:
  name, description, tier (select), content (Monaco markdown editor), enabled. Slug auto-derived
  from name, editable. Wired to a TanStack Query mutation.
- **Data layer:** hooks in `apps/web-ui/lib/queries/skills.ts`, keys in
  `apps/web-ui/lib/queries/query-keys.ts`; invalidate on mutation; sonner toasts.

## Consumption (auto-populate from DB)

- **AI Ops chat:** the skill dropdown in `components/agent/chat-interface.tsx` already fetches
  `/api/skills`; it now returns tenant DB skills filtered to `isEnabled`. No UI rework beyond
  the data source. Disabled skills excluded.
- **Agent Ops:** the evaluator node in `executor-graphs.ts` lists skills from the DB
  (tenant-scoped) instead of the filesystem; auto-pick logic unchanged. Disabled skills excluded.

## Chat → Skill Conversion

- "Save as skill" action in the AI Ops chat console (chat actions menu / end of conversation).
- Calls `POST /api/skills/distill` with the current `threadId` → LLM distills transcript into a
  draft (name, description, suggested tier, step-by-step procedure).
- Draft opens the **same create-skill dialog pre-filled**; user reviews/edits and saves.
- Saved skill: `source: "user"`, `sourceRunId: threadId`, `createdBy: userId`.

## RBAC

- New `Skill` subject in `apps/web-ui/lib/rbac/types.ts` with actions `read | create | update
  | delete`, wired into the role-permission matrix (admins full CRUD, viewers read-only).
- All mutating routes call `authorize(action, 'Skill')`.

## Out of Scope (future, accommodated)

- The cron/automation that auto-generates `source: "system"` skills is **not built now**. The
  model, the `source` field, and the create path already accommodate it — a future worker job
  inserts `Skill` rows with `source: "system"`.

## Testing

- Repo-level tenant-isolation test for `Skill` (multitenancy convention — `$executeRaw` not
  used here; standard tenant client).
- Service tests for `loadSkills` / `getSkillContent` (enabled filtering, tenant scoping).
- API route tests including RBAC 403 paths for create/update/delete.
- One Playwright E2E: create a skill in the console → it appears in the AI Ops dropdown.

## Risks / Notes

- **Async conversion of agent call sites** is the main blast radius — `getSkillContent` /
  `buildEffectiveSkillSection` go from sync to async and gain a `tenantId` param. Must update
  every caller (table above) and confirm `tenantId` is plumbed through the graph config.
- Per-request cache prevents N DB hits per agent run (reflector loops re-inject skill content).
- No data migration needed (filesystem deleted, built-ins re-created via console).
