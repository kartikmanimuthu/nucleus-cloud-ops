**Account model** (`@@map("accounts")`):
```prisma
model Account {
  id               String   @id @default(cuid())
  tenantId         String
  accountId        String                          // AWS account ID (12-digit string)
  name             String
  roleArn          String
  externalId       String?
  regions          String[]
  active           Boolean  @default(true)
  description      String?
  connectionStatus String   @default("unknown")
  connectionError  String?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt
  createdBy        String   @default("system")
  updatedBy        String   @default("system")

  @@unique([tenantId, accountId])
  @@index([tenantId])
  @@index([tenantId, active])
  @@map("accounts")
}
```

**UserTenantRole model** (`@@map("user_tenant_roles")`):
```prisma
model UserTenantRole {
  id         String   @id @default(cuid())
  userId     String                              // Cognito sub
  tenantId   String
  email      String
  role       String                              // CHECK in migration SQL: SuperAdmin|TenantAdmin|TenantOperator|TenantViewer
  assignedAt DateTime @default(now())
  assignedBy String

  @@unique([userId, tenantId])
  @@index([tenantId])
  @@map("user_tenant_roles")
}
```

Note on `role` field: Prisma does not natively emit CHECK constraints via `@db.Check`. Use `String` type here. The migration SQL must be patched after generation (Task 2) to add `CHECK (role IN ('SuperAdmin','TenantAdmin','TenantOperator','TenantViewer'))`.

Note on Tenant relation: Do NOT add a `@relation` to Tenant for Account or UserTenantRole. The tenantId is a plain string reference (not enforced FK), consistent with how DynamoDB stored tenant scope. This avoids requiring all tenants to exist in the tenants table before migration.
