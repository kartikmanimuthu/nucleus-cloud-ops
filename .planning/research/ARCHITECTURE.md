## Data Flow (After Migration)

```
API Route → Service → Repository Factory
                         ↓ (feature flag)
                    ┌────┴────┐
                    │ DynamoDB │  ← rollback path
                    │   Repo   │
                    └─────────┘
                    ┌─────────┐
                    │PostgreSQL│  ← target path
                    │   Repo   │
                    └─────────┘
```

Lambda functions follow the same pattern but with separate connection pooling (max: 3).

## Suggested Build Order (dependency-driven)

1. **Foundation** — Docker Compose, Drizzle config, pg-config.ts, repository-factory.ts, schema directory
2. **Tenant Config** — Zero dependencies, simple CRUD, ~4 API routes, no Lambda consumers
3. **Accounts + RBAC** — Accounts referenced by schedules (FK). RBAC is standalone table.
4. **Schedules + Executions + Audit** — Schedules depend on accounts (FK). Includes scheduler Lambda. Highest risk.
5. **Knowledge Base + Inventory + Vector** — KB depends on tenants. Inventory is Python Lambda (psycopg2).
6. **Agent Ops** — Dynamoose rewrite. Self-contained, no FK deps on other migrated tables. Most complex.
7. **LangGraph Persistence** — Checkpoints, writes, chat history, memory. Switch @farukada → @langchain/langgraph-checkpoint-postgres.

Note: Phases 5-7 could potentially run in parallel since they have no FK dependencies on each other.

## DynamoDB → PostgreSQL Schema Mapping

| DynamoDB Pattern | PostgreSQL Equivalent |
|-----------------|----------------------|
| Composite PK (pk + sk) | Separate tables with proper PKs |
| GSI1/GSI2/GSI3 | B-tree indexes + WHERE clauses |
| Single-table design | Normalized relational tables |
| TTL (expire_at) | expires_at column + cleanup cron |
| Condition expressions | PostgreSQL constraints + ON CONFLICT |
| Query + FilterExpression | WHERE clause (pushed to DB) |
| Scan + client filter | WHERE + ORDER BY + LIMIT |
| DynamoDB Streams | PostgreSQL triggers or LISTEN/NOTIFY (if needed) |
