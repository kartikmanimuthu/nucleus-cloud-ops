# Quick Task 260408-32q: Fix discovery scanner stuck — Summary

## What Changed

**File:** `workers/src/jobs/discovery/services/scanner.ts`

**Root Cause:** `invokeService()` had an infinite pagination loop. It read next-page tokens from multiple AWS response fields (`NextToken`, `Marker`, `NextPageToken`, `nextToken`) but always sent the token back as `NextToken`. AWS APIs that use `Marker` for pagination (IAM `list_roles`, `list_users`) ignored the `NextToken` input, returned the same first page with `IsTruncated: true`, and the scanner looped forever.

**Fix:** Track which response field contained the pagination token and mirror it back with the correct input parameter name. For example, if the response has `Marker`, send it back as `Marker`; if `NextMarker`, send as `Marker`; if `NextToken`, send as `NextToken`.

## Bug 2: search_vector trigger column name mismatch

**File:** `prisma/migrations/20260405_add_inventory_search_vector/migration.sql`

**Root Cause:** The migration created a trigger referencing `NEW.search_vector` (snake_case), but Prisma maps the model field `searchVector` to a camelCase column `"searchVector"`. The trigger fired on INSERT but failed because the column name didn't match.

**Fix:** Updated the trigger function and migration to use `NEW."searchVector"` and `"searchVector"` everywhere. Also applied the fix to the live database.
