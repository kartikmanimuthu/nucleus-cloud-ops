<objective>
Fix tenant isolation and PostgreSQL migration gaps in the AI Ops agent layer.

Purpose: The agent tools (get_aws_credentials, list_aws_accounts) currently leak cross-tenant data because tenantId is not passed to account lookups. Additionally, agent-shared.ts has its own checkpointer/store init that bypasses the USE_PG_LANGGRAPH feature flag, and the chat route still seeds session metadata to DynamoDB.

Output: Tenant-scoped agent tools, unified PG-aware persistence in agent layer, PG-first session metadata.
</objective>

  <name>Task 2: Unify agent persistence to respect PG feature flag + migrate session metadata</name>
  <files>web-ui/lib/agent/agent-shared.ts, web-ui/app/api/chat/route.ts</files>
  <action>
Two issues: agent-shared.ts has duplicate checkpointer/store init that ignores USE_PG_LANGGRAPH, and chat route seeds session metadata to DynamoDB.

1. **agent-shared.ts — getCheckpointer() (lines 486-509):**
   Currently checks `DYNAMODB_CHECKPOINT_TABLE` env var and always uses DynamoDB if set, ignoring `USE_PG_LANGGRAPH`. The `persistence.ts` module already has a proper feature-flag-aware `getCheckpointer()`.
   - Replace the entire `initCheckpointer()` / `getCheckpointer()` / `globalForCheckpointer` block with a simple re-delegation to `persistence.ts`'s `getCheckpointer()`.
   - The persistence.ts version already uses globalThis for singleton and checks USE_PG_LANGGRAPH first.
   - Keep the FileSaver fallback only when NEITHER DynamoDB env vars NOR DATABASE_URL are set.

2. **agent-shared.ts — getStore() (lines 511-516):**
   Only returns DynamoDBStore when `DYNAMODB_MEMORY_TABLE` is set. Never returns PostgresMemoryStore.
   - Replace with delegation to `persistence.ts`'s `getMemoryStore()`.
   - When USE_PG_LANGGRAPH=true, persistence.ts returns PostgresMemoryStore.
   - When DynamoDB env vars are set, returns DynamoDBStore.
   - Return type should be `MemoryStoreInterface` (the common interface from persistence.ts) or the union type.

3. **chat/route.ts — session metadata seeding (lines 101-124):**
   The `if (process.env.DYNAMODB_CHAT_HISTORY_TABLE)` block on line 101 seeds session metadata directly to DynamoDB. The else branch uses file-based threadStore.
   - Restructure: check `USE_PG_LANGGRAPH === 'true'` first. When PG is active, use the threadStore (or create a PG-based session record via Prisma ChatMessage or a dedicated threads table).
   - Actually, the threadStore is file-based. For PG mode, the session metadata should be handled by the PostgresChatHistory from persistence.ts — the `addMessages` call later in the route already handles this.
   - Simplest fix: when USE_PG_LANGGRAPH=true, skip the DynamoDB metadata seeding entirely. The thread will appear in the sidebar when messages are persisted via the existing `chatHistory.addMessages()` call in the finally block.
   - When USE_PG_LANGGRAPH is NOT true and DYNAMODB_CHAT_HISTORY_TABLE is set, keep existing DynamoDB seeding.
   - When neither, keep the file-based threadStore fallback.

4. **chat/route.ts — message persistence in finally block (lines 688-737):**
   The `if (process.env.DYNAMODB_CHAT_HISTORY_TABLE)` guard on line 688 means PG mode never persists messages in the streaming path.
   - Change condition to: `if (process.env.DYNAMODB_CHAT_HISTORY_TABLE || process.env.USE_PG_LANGGRAPH === 'true')`.
   - Same fix for the non-streaming path on line 323.
