Text-to-SQL Agent — Error Handling & Testing

How failures are handled at each stage, and the testing strategy

Error Handling by Node

describe_schema
If fails: DB connection error → return friendly error to user ("Unable to connect to inventory database"). No retries — this is a hard dependency.
Caching: Schema is cached in state after first successful call. Follow-up questions in the same conversation skip this node.
generate_sql
If LLM fails: Bedrock timeout/throttle → retry once, then error to user.
If SQL invalid: Validator rejects (not SELECT, missing tenant_id, forbidden table) → feed validation error back as reflection feedback, retry generation.
Prompt includes: Schema, question, conversation history, and any prior error/feedback from reflection.
execute_sql
If SQL error: Syntax error, invalid column, etc. → capture error message, pass to reflect node. The reflection loop will generate corrected SQL.
If timeout: 10s statement_timeout hit → error captured, reflection suggests simpler query or adding indexes.
If connection error: Pool exhausted → error to user ("Database temporarily unavailable").
reflect
If not satisfied + retries left: Feedback goes back to generate_sql with specific guidance ("Try using JSONB operator for tags", "Column name is resource_type not type").
If not satisfied + max retries (3): Proceed to synthesize anyway with best available results. User gets answer with a note: "I had difficulty finding the exact answer. Here's what I found..."
Empty results: Not always an error. Reflector checks if "zero results" is a valid answer (e.g., "no Lambda functions in eu-west-1" is correct if there aren't any).
synthesize
If LLM fails: Return raw query results as a formatted table (graceful degradation).
Streaming: Tokens stream via SSE. If client disconnects mid-stream, server detects abort signal and cleans up.

Testing Strategy

Unit Tests (Vitest)
sql-validator.test.ts
• Rejects INSERT/UPDATE/DELETE/DROP
• Rejects queries without $1 tenant param
• Rejects queries referencing non-allowed tables
• Appends LIMIT 500 when missing
• Passes valid SELECT queries
prompts.test.ts
• Schema description formatting
• Filter injection into prompts
Integration Tests (Vitest)
graph.test.ts
• Mock LLM + real pg pool against test DB
• Full graph execution: question → SQL → results → answer
• Reflection loop triggers on bad SQL
• Max retries respected
• Tenant isolation enforced
execute-sql.test.ts
• Read-only transaction blocks writes
• Statement timeout fires at 10s
• Parameterized queries prevent injection
E2E Tests (Playwright)
ask-ai-sql.spec.ts
• Open Ask AI → type question → see step indicators
• SQL block appears and is collapsible
• Answer streams in with markdown table
• Follow-up question uses conversation context
• Error state renders correctly
Security Tests (Vitest)
sql-validator.security.test.ts
• SQL injection attempts blocked
• Subquery attacks (SELECT from auth_users) blocked
• UNION-based table access blocked
• Comment-based bypass attempts blocked
• Tenant ID cannot be overridden

Edge Cases

Ambiguous question — "show me everything" → agent generates broad SELECT with LIMIT 500, synthesizer summarizes by resource type
JSONB queries — "resources tagged Environment=Production" → agent uses tags->>'Environment' = 'Production' or tags @> '{"Environment":"Production"}'
No data — empty inventory → describe_schema still works, agent returns "No inventory data found. Run a sync first."
Non-inventory question — "what's the weather?" → agent recognizes no relevant SQL, returns "I can only answer questions about your AWS inventory."
Large result sets — LIMIT 500 cap + synthesizer summarizes/aggregates rather than listing all 500 rows
Metadata queries — "instances with more than 4 vCPUs" → agent uses metadata->>'vCpuCount' JSONB access
