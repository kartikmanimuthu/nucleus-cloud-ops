Text-to-SQL Agent — Architecture Approaches

Three ways to build the LangGraph reflection agent for inventory queries

A

Standalone LangGraph Agent (Recommended)

New dedicated agent in web-ui/lib/agent/text-to-sql/ with its own StateGraph, separate from the existing fast/planning agents.

User Question
→ generate_sql (LLM + schema context)
→ execute_sql (Prisma $queryRawUnsafe, read-only)
→ reflect (LLM evaluates: did this answer the question?)
→ if not satisfied → back to generate_sql (max 3 retries)
→ synthesize (LLM formats natural language answer)
→ Stream to user

Pros

  • Clean separation — doesn't touch existing agent code
  • Purpose-built state for SQL generation (schema, query history, errors)
  • Easy to test and iterate independently
  • Reuses model-factory.ts for Bedrock access

Cons

  • New module to maintain alongside existing agents
  • Doesn't inherit MCP tools or memory from fast-agent
B

Extend Fast Agent with SQL Tool

Add a query_inventory_sql tool to the existing fast-agent's toolset. The agent decides when to use SQL vs other tools.

User Question
→ fast-agent (existing reflection loop)
→ agent calls query_inventory_sql tool
→ tool internally: generate SQL → execute → return results
→ fast-agent reflects on tool output
→ Stream answer

Pros

  • Reuses existing agent infrastructure
  • Agent can combine SQL with other tools
  • Less new code

Cons

  • SQL self-correction is hidden inside a single tool call
  • Fast-agent's reflection loop isn't SQL-aware
  • Harder to stream step-by-step progress
  • Mixes concerns — inventory SQL + general agent ops
C

Vercel AI SDK Agent (Lightweight)

Use Vercel AI SDK's streamText with tool calls instead of LangGraph. Simpler but less structured reflection.

User Question
→ streamText with tools: [generate_sql, execute_sql, reflect]
→ LLM orchestrates tool calls in sequence
→ maxSteps: 10 allows multi-turn tool use
→ Final text streams to user

Pros

  • Minimal code — leverages existing Vercel AI SDK
  • Built-in streaming
  • No LangGraph dependency for this feature

Cons

  • No explicit state graph — reflection is implicit via maxSteps
  • Harder to control the exact flow (generate → execute → reflect)
  • Inconsistent with existing agent architecture (LangGraph)
  • Less observable — can't easily show "which step am I on"

Click an approach to select it. I recommend Approach A — it gives you a purpose-built SQL reflection loop with clean step-by-step streaming, without touching the existing agent code.
